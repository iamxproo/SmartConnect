# Migrations

Each service owns its migrations in `smartconnect-backend/services/<svc>/prisma/migrations/`, and its history in `<svc>._prisma_migrations`. Migrations run as the service's **migrator** role, which can change nothing outside its own schema. A migration that touches another schema fails with `permission denied`.

## Rules

1. **Forward-only.** Never edit or delete an applied migration (Prisma checksums them). Fix forward with a new migration. *Pre-production exception:* until the first production deployment, `*_init` migrations may be regenerated by team agreement.
2. **Never `prisma db push`** and never `prisma migrate reset` / `migrate dev` against the dev database. Both can drop data. Authoring uses `make db-migration`, which diffs against a throwaway shadow database on the test instance.
3. **Never run destructive changes automatically.** Drops, type narrowing and `SET NOT NULL` on populated tables follow [destructive changes](#destructive-changes).
4. **Every migration is atomic.** `make db-migration` wraps the SQL in `BEGIN … COMMIT` because Prisma does not ([verified](#prisma-710-behaviours-verified)).
5. **Every new tenant table gets RLS** in the same migration (`make db-test` fails otherwise).
6. **Migrations never reference role names.** Grants come from default privileges set by the bootstrap, so the same migration works in every environment.

## Daily workflow

```bash
# 0. once: infrastructure + credentials
make install && make infra-up && make db-bootstrap
make test-db-up                                  # shadow-database host for authoring

# 1. edit services/<svc>/prisma/schema.prisma
cd smartconnect-backend/services/messaging && npx prisma format && npx prisma validate && cd -

# 2. generate the migration (diffs migrations → schema in a fresh shadow DB on the TEST instance)
make db-migration SERVICE=messaging NAME=add_pinned_messages
#    hand-written only (policies, functions, data fixes; no schema.prisma change):
make db-migration SERVICE=messaging NAME=tighten_policy EMPTY=1

# 3. review the SQL; add hand-written SQL (RLS, CHECKs) ABOVE the final COMMIT

# 4. rehearse on a fresh test instance, then apply to dev
make db-test                                     # migrates a fresh instance from zero + runs 393 checks
make db-migrate                                  # prisma migrate deploy for every service, then re-asserts privileges
make db-status && make db-drift
make prisma-generate && make typecheck
```

### Review checklist

- [ ] SQL matches intent; no unexpected `DROP` (the tool prints a warning when it sees one)
- [ ] New tenant table: `organization_id NOT NULL`, `@@unique([organizationId, id])` if it is a parent, composite relations, and `ENABLE ROW LEVEL SECURITY` + `tenant_isolation` policy appended
- [ ] Indexes match the queries that will use them; large-table index builds planned (see below)
- [ ] New `SECURITY DEFINER` function: `SET search_path = pg_catalog, pg_temp`, qualified names, ids-only result, clamped inputs
- [ ] Backward compatible with the currently deployed service version (expand/contract)
- [ ] `make db-test` and `make db-drift` green

## How the tooling works

| Command | Does | Touches |
|---|---|---|
| `make db-bootstrap` | Applies `010_bootstrap.sql`, provisions/keeps per-service passwords, writes `.env` + `.env.migration`, verifies 28 logins | dev |
| `make db-migrate` | `prisma migrate deploy` per service with its `MIGRATION_DATABASE_URL` (asserted to be the migrator role), then re-applies the bootstrap (privilege re-assertion, `_prisma_migrations` revoke, append-only revoke) | dev |
| `make db-status` | `prisma migrate status` per service | dev (read-only) |
| `make db-migration SERVICE= NAME= [EMPTY=1]` | Creates a fresh shadow DB `shadow_<svc>` on the **test** instance, runs `prisma migrate diff --from-migrations --to-schema --script`, wraps the result in a transaction, writes `prisma/migrations/<UTC timestamp>_<name>/migration.sql`, drops the shadow DB | test only |
| `make db-drift` | Same diff with `--exit-code`, for all services. Fails on any difference | test only |
| `make db-rehearse` | Bootstrap + ephemeral credentials + all migrations, as migrators, on the test instance | test only |
| `make db-test` | Recreates the test instance and runs the database suites (migrations from zero, privileges, RLS, backup/restore) | test (reads dev) |

Prisma itself is configured per service in `prisma.config.ts`: `datasource.url = MIGRATION_DATABASE_URL`, `shadowDatabaseUrl = SHADOW_DATABASE_URL` (injected by the tool). Running `npx prisma migrate deploy` inside a service directory also works (it loads `.env.migration`).

## Hand-written SQL in migrations

Prisma does not model RLS policies, CHECK constraints, functions or triggers, and its diff ignores them (verified: drift checks stay green with them present). They live below the generated SQL in the same migration file, under a `Hand-written SQL` banner, as in every `*_init` migration.

## Destructive changes

Use **expand → migrate → contract** across releases. Never drop in the same release that stops using a column.

| Change | Safe procedure |
|---|---|
| Drop column/table | Release N: stop reading/writing it. Release N+1: migration drops it (after a backup check) |
| Rename column | Add new column → dual-write → backfill (as migrator, batched) → switch reads → drop old |
| `SET NOT NULL` on a big table | Add `CHECK (col IS NOT NULL) NOT VALID` → `VALIDATE CONSTRAINT` (no long lock) → `SET NOT NULL` → drop the check |
| Change type | New column + backfill as above |
| Remove enum value | Avoid. Create a new enum type and migrate the column |
| Index on a large table | `CREATE INDEX CONCURRENTLY` as the **only statement** in its own migration (cannot run in a transaction; the tool leaves it unwrapped and warns). At current volumes plain `CREATE INDEX` is fine |

Migrator sessions have `lock_timeout = 10s`. A migration that cannot get its lock fails fast instead of queueing behind traffic. Retry it off-peak.

## Production execution

1. CI builds the service image and runs `make db-drift` + `make db-test` (green required).
2. The deploy pipeline runs a **migration Job per service** before rolling out that service: `prisma migrate deploy` with **only** the migrator secret from the secrets manager. Services are independent, so their order doesn't matter.
3. The pipeline then re-applies `010_bootstrap.sql` as the platform admin role (idempotent privilege re-assertion).
4. Roll out the service (runtime secret only).
5. `prisma migrate status` must report up to date. Alert otherwise.

Migrations are never run on service start-up: replicas would race and runtime pods would need DDL rights.

### Failed migration recovery

Migrations generated by the tool are wrapped in a transaction, so a failure leaves **no partial changes**. Prisma still records the migration as failed and blocks further deploys (`P3009`):

```bash
cd smartconnect-backend/services/<svc>
npx prisma migrate resolve --rolled-back <migration_name>   # nothing was applied (transaction rolled back)
# fix forward: correct the SQL in that (never-applied) migration, or add a new one; then
npx prisma migrate deploy
```

For an *unwrapped* migration (e.g. `CONCURRENTLY`), inspect what was applied first. Then either complete it by hand and `migrate resolve --applied`, or undo it and `--rolled-back`.

## Development seed

`make db-seed` loads one demo tenant (*Acme Demo*: 2 users, roles, workspace `acme-hq`, channel `#general`, a welcome message, default retention policies). See [`scripts/seed-dev.ts`](../../smartconnect-backend/scripts/seed-dev.ts).
- Writes through **each service's own runtime credentials and Prisma client** inside `withTenant()`, so it obeys the same ownership and RLS rules as production code.
- Idempotent (fixed ids + upserts; verified by running twice). It refuses to run unless every target URL is `localhost/smartconnect` and `NODE_ENV` is not `production`.
- It writes no outbox events, so it seeds the messaging membership projection directly.
- Tests never depend on seed data; they create their own random tenants.

## Prisma 7.10 behaviours (verified)

Each item was reproduced on 2026-11-02 against Prisma 7.10.1 and PostgreSQL 16.15.

| Behaviour | Consequence / mitigation |
|---|---|
| Prisma 7 moved connection URLs to `prisma.config.ts`, no longer auto-loads `.env`, and requires `output` for the `prisma-client` generator | Each service's `prisma.config.ts` loads `.env.migration` via `process.loadEnvFile()` (never overrides real env vars) |
| `migrate diff` **exits 0 with no output** when no datasource URL is configured (schema engine silently fails) | `prisma.config.ts` always supplies a URL (an unreachable placeholder for offline commands). The tool accepts only Prisma's explicit `-- This is an empty migration.` marker as "nothing to generate" and fails on empty output |
| `--from-migrations` needs `migration_lock.toml` even for an empty migrations dir; the shadow DB must already exist (`P1003`) | `db.mjs` writes the lock file first and creates/drops `shadow_<svc>` on the test instance |
| `CREATE SCHEMA IF NOT EXISTS "x"` fails with `permission denied for database` for a role without database CREATE, **even when the schema exists** | Schemas are pre-created and owned by migrators; `--from-migrations` diffs do not emit the statement for existing schemas; the tool rewrites it into a guarded `DO` block if it ever appears |
| **Migrations are not atomic**: a failure leaves earlier statements applied and blocks deploys (`P3009`) | The tool wraps migrations in `BEGIN … COMMIT` (verified: full rollback, then `migrate resolve --rolled-back` + redeploy succeeds) |
| `partialIndexes` (preview): `status IN (…)` predicates are stored by PostgreSQL as `= ANY (ARRAY[…])`, which Prisma reports as drift forever | Write partial-index predicates with `=` / `OR` / `IS [NOT] NULL` only |
| Optional composite relations default to `ON DELETE RESTRICT` (never nulling the tenant column) | Composite tenant FKs are used for optional relations too, with explicit `Cascade` where intended |
| `@unique` / `@@unique` become unique **indexes**, not constraints | Catalog tooling (ERD generator) reads `pg_index` |
| `INSERT … RETURNING` (Prisma `create`) must satisfy SELECT policies | Write-only rows (platform audit events) use `createMany` |
| Nested `create` inherits `organization_id` through a composite relation and rejects an explicit value | Nested writes cannot diverge from the parent's tenant |
| `npm` dist-tag `latest` for `prisma` was `8.0.0-rc.29` while `@prisma/client` was `7.10.1` | Exact versions pinned in every `package.json`; never install `@latest` |
